# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a fork of the Refal-05 compiler - a Refal-5 subset compiler that compiles to C89.
The only thing the fork changes is the build: it is **self-contained** and does not require an external Refal-5 compiler for bootstrapping.
Instead it stores pre-compiled C artifacts from previous builds in `bootstrap/` and uses them to rebuild the compiler with itself.

Upstream is https://github.com/Mazdaywik/Refal-05, tracked as the `upstream` remote.
The fork is currently synced to upstream commit `0ffeece`.

## Ownership rule

**Never modify or delete a file that belongs to upstream.**
Every upstream-owned file in this repo is byte-identical to `upstream/master`, which is what keeps `git merge upstream/master` almost conflict-free.
An earlier version of this fork ignored that rule and paid for it: commit `4cc6795` stripped ~2300 non-breaking spaces out of `docs/` and `README.md`, replaced the upstream README wholesale and rewrote both test runners, which turned the next upstream merge into 17 conflicts.

Files that belong to the fork, and are the only ones you may freely change:

- `bootstrap/`
- `framework/` (a submodule; the pin is ours, the contents are not)
- `Makefile`
- `src/standalone-bootstrap.sh`, `src/standalone-bootstrap.cmd`
- `autotests/run.sh`, `autotests/run.cmd`
- `.github/`
- `CLAUDE.md`
- the fork section at the top of `README.md`, above the `---` separator

`README.md` is the one deliberate exception: upstream's text is preserved verbatim below the separator, and the fork's section is prepended.
Keep that section short so it stays trivial to re-merge.

If something needs fixing in an upstream-owned file, send it upstream instead of patching it here.

## Bootstrap Architecture

1. **Bootstrap artifacts**: pre-compiled C files in `bootstrap/`, generated by the previous compiler build
2. **Stage 1**: compile the old compiler (`bin/refal05c-old`) from the bootstrap C files
3. **Stage 2**: use the old compiler to recompile `src/*.ref` and the framework modules into fresh C files
4. **Stage 3**: compile the new compiler (`bin/refal05c`) from the newly generated C files
5. **Validation**: run the autotests against the new compiler

**Every file in `bootstrap/` is regenerated on every bootstrap. There are no frozen artifacts.**

Its eight files come from two source trees:

- the compiler itself, from `src/`: `main.c`, `generator.c`, `parser.c`
- the Refal-5 framework, from `framework/`: `LibraryEx.c`, `R5FW-Parser.c`, `R5FW-Plainer.c`, `R5FW-Transformer.c`, `Platform.c`

`framework/` is a git submodule pinned to a commit of [refal-5-framework](https://github.com/Mazdaywik/refal-5-framework), so the provenance of those sources is recorded by git itself rather than by a convention.
The compiler compiles them, exactly as upstream's own build does in `src/makeself.sh`, so no external toolchain is involved.
Modules are referenced at their real paths: `framework/lib/*.ref`, and `framework/lib/posix/Platform.ref`.

`Platform.ref` is taken from `lib/posix/` on **both** platforms, deliberately: its `PathSeparator` returns `:`, so `R05PATH` is colon-separated everywhere.

Both bootstrap scripts run `git submodule update --init framework` if the submodule is missing, and fail with an explicit message if that does not work, so a non-recursive clone gives a clear error rather than a confusing compile failure.
Every checkout in CI uses `submodules: recursive`.

This used to be otherwise, and the history is worth knowing.
Those five files were once committed as frozen C with no source in the repo, regenerable only with an external Refal-5, and drifting further from the framework with every framework release - the fork was carrying stale compiled output of somebody else's actively developed project.
The frozen set was a framework version behind, still carrying a separate `R5FW-Parser-Defs.c` that the framework had already merged into `R5FW-Parser.ref`, and it worked only because the interface happened not to have changed.
It turned out none of that was necessary.

The framework revision is bumped automatically, by its own job in the weekly sync, in its own pull request.
Keeping it separate from the Refal-05 sync is deliberate: the two upstreams fail independently, so a framework change that breaks the bootstrap does not also block an unrelated Refal-05 update from landing.

### Where generated `.c` files land

The compiler derives the output path by stripping everything up to the last directory separator, but `IsDirectorySeparator` in `bootstrap/Platform.c` recognizes **only `/`**, never `\`.
The consequence is platform-dependent and easy to mistake for a typo:

- Linux: `bin/refal05c src/main` writes `./main.c` into the current directory, so `src/standalone-bootstrap.sh` collects everything with `mv *.c bootstrap`
- Windows: `bin\refal05c.exe src\main` writes `src\main.c` (the backslash is not stripped), so `src\standalone-bootstrap.cmd` collects from **both** source directories, with `move /Y src\*.c bootstrap\`, `move /Y framework\lib\*.c bootstrap\` and `move /Y framework\lib\posix\*.c bootstrap\`

Do not "unify" those two collection commands - each is correct for its platform.

`bootstrap/Platform.c` is the POSIX-flavoured build on both platforms for the same reason: its `PathSeparator` returns `:`, so `R05PATH` is colon-separated even on Windows.

## Build Commands

### Linux/Unix

```bash
make bin/refal05c
```

This creates `c-plus-plus.conf.sh` from `lib/c-plus-plus.conf.sh.template` if missing, runs `src/standalone-bootstrap.sh` for the full 3-stage bootstrap, and then runs the autotests.

```bash
./autotests/run.sh

./autotests/run.sh arithmetic-32-bit.ref bad-comment.BAD-SYNTAX.ref
```

### Windows

```cmd
make bin/refal05c.exe
```

Or directly: `src\standalone-bootstrap.cmd`.

`make bin/refal05c.exe` copies `c-plus-plus.conf.cmd` from `lib/c-plus-plus.conf.cmd.template`, but the template has no active compiler - it aborts with `C++ compiler is not selected` until you uncomment one of the sections (Visual C++, MinGW, Clang, Borland, Watcom).

```cmd
autotests\run.cmd

autotests\run.cmd arithmetic-32-bit.ref bad-comment.BAD-SYNTAX.ref
```

### Test runner behaviour

Both runners can be run from any directory, detect the test type from the filename suffix, and report a pass/fail summary with a non-zero exit code on failure.

- `.BAD-SYNTAX.ref` - compilation must fail with an error, and the compiler must not crash (exit code < 200)
- `.SATELLITE.ref` - helper module, compiled together with the test of the same base name, never run on its own
- `nested-comment.BAD-SYNTAX._ref` - disabled; the `._ref` extension keeps it out of the `*.ref` glob

**Do not replace these with upstream's runners.** Upstream's `autotests/run.sh` calls bare `exit` on every failure path, which exits with the status of the preceding `echo` - that is, `0` - so it can never fail CI.

The fork's own `run.sh` had a matching defect until this sync: it was called from an `if` condition, which suppresses `set -e` inside the function, and it passed `$BASENAME.SATELLITE.c` to the C compiler unconditionally.
For every test without a satellite the C compilation failed with "No such file or directory", the error went to `/dev/null`, no binary was produced, and the test was reported `OK`.
Only `mu.ref` and `mu-uses-all.ref` were genuinely compiled and executed; the other 32 non-`BAD-SYNTAX` tests were silent no-ops.
Both runners now check every step explicitly.

### Cleanup

```bash
make clear
```

Runs upstream's `clear.sh` (removes `bin`, `src/cfiles`, `src/rsl`) and deletes stray `*.c` left in the project root by a failed bootstrap.

## Key Directories and Files

- `src/` - compiler source code, written in Refal:
  - `main.ref` - driver and compiler utilities
  - `parser.ref` - parser
  - `generator.ref` - C code generator
  - `standalone-bootstrap.sh` / `standalone-bootstrap.cmd` - **the fork's** bootstrap scripts
  - `makeself.sh` / `makeself.cmd` - upstream's bootstrap, requires an external Refal-5 (`refc`/`refgo`) or `rlmake`; not used here
  - `benchmark.sh` / `benchmark.cmd`, `benchmark.prj` - upstream's benchmarking scripts, not exercised by CI

- `bootstrap.sh` / `bootstrap.cmd` at the repo root are **upstream's** entry points and call `src/makeself.*`, so they need an external Refal-5 and will not work standalone. Use `make bin/refal05c` instead.

- `bootstrap/` - generated C artifacts, committed; regenerated in full by every bootstrap

- `framework/` - submodule with the Refal-5 framework sources; never edit anything inside it, send fixes to that repository

- `lib/` - runtime and standard library:
  - `refal05rts.c` / `refal05rts.h` - runtime support
  - `refal05bif.c` - built-in Refal functions
  - `Go.c` - aliases entry point `GO` to `Go`; **not linked** by any build or test script, so `$ENTRY GO` is the only entry point that actually works here
  - `c-plus-plus.conf.sh.template` / `c-plus-plus.conf.cmd.template` - C compiler configuration templates

- `autotests/` - test suite and runners

- `docs/` - Russian language documentation (`1-intro.md` ... `4-implementation.md`, `A-style-guide.md`)

- `examples/` - `lambda.ref`, and `filesize-test.ref` + `filesize.c` showing how to extend Refal-05 with a custom C function

- `bin/` - build output, gitignored: `refal05c` / `refal05c.exe` and the intermediate `refal05c-old`

- `c-plus-plus.conf.sh` / `c-plus-plus.conf.cmd` - created from the templates at the project root, both gitignored

## C Compiler Configuration

Default on Unix: `export R05CCOMP='gcc -Wall -g'`.

Flags worth knowing:

- `-DR05_SHOW_STAT` - show compiler statistics; used by the bootstrap scripts
- `-DR05_SHOW_STAT_DETAILED` - enables the per-function profiling hooks; without it `r05_this_is_generated_function`, `r05_start_e_loop` and `r05_stop_e_loop` compile to no-op macros
- `-DR05_NUMBER_INT` (default), `-DR05_NUMBER_LONG`, `-DR05_NUMBER_LONGLONG`, `-DR05_NUMBER_UINT32_T`, `-DR05_NUMBER_UINT64_T`, `-DR05_NUMBER_CUSTOM` - macro-digit size

Two flags the old configuration used are now obsolete: `-DR05_POSIX` (`refal05rts.h` auto-detects the platform and errors if both `R05_POSIX` and `R05_WINDOWS` are set) and `-DR05_CLOCK_SKIP` (no longer referenced anywhere in the runtime).

CI does not use the Windows template at all: `.github/workflows/build.yml` writes its own `c-plus-plus.conf.cmd` with `cl /TC /W3 /wd4996 /O2`, where `/TC` forces the sources to be compiled as C rather than C++.

The MSVC workaround this fork used to carry - replacing the tentative definition `static struct builtin_info s_builtin_info[];` with a fixed-size array - is **no longer needed**.
Upstream reordered `lib/refal05bif.c` so the table is defined before all of its users, and there is no forward declaration left to trip over.

## Compiler Usage

```bash
R05PATH=/path/to/repo/lib bin/refal05c hello refal05rts refal05bif
```

This generates `hello.c` in the **current working directory** and, if `R05CCOMP` is set, an executable.

`R05PATH` is mandatory here: `refal05rts` and `refal05bif` are resolved as bare module names and their `.c` files live in `lib/`, which the compiler does not search by default.
Without it the run fails with `COMMAND LINE ERROR: file refal05rts not found`.
`R05PATH` is colon-separated on every platform (see `bootstrap/Platform.c`).

The bootstrap and test scripts sidestep this by passing explicit paths (`./lib/refal05bif ./lib/refal05rts`) or by handing the runtime `.c` files straight to the C compiler.

## Modifying the Compiler

When changing `src/*.ref` - which should be rare, since those are upstream's files:

1. Make the change
2. Run `make bin/refal05c` or `src/standalone-bootstrap.sh`
3. The old compiler compiles the change, `bootstrap/main.c`, `bootstrap/generator.c` and `bootstrap/parser.c` are replaced with the newly generated C, the new compiler is built from them, and the autotests run

The regenerated `bootstrap/*.c` files are **committed** - they are the seed for the next build, so a source change is only complete once the updated C artifacts are committed alongside it.

## Updating from upstream

```bash
git fetch upstream
git merge upstream/master
```

Resolve by ownership: take upstream's version for every upstream-owned file, keep ours for the fork-owned list above.

If upstream renamed or split modules, update the module lists in `src/standalone-bootstrap.sh` and `src/standalone-bootstrap.cmd` (each names the modules twice - once as Refal sources, once as generated C files), then bootstrap.

Verify the result by reaching a **fixpoint**: regenerate the C, rebuild, regenerate again, and require the second and third generations to be byte-identical.
A successful build alone does not prove the update took.

### Upstream-sync PRs must be merged as merge commits

The whole point of a sync PR is the second parent: it records the upstream commit as an ancestor of `master`, which is what makes the next `git merge upstream/master` a no-op instead of a re-resolution of everything already settled.

Squash and rebase both destroy that, silently and irreversibly once `master` moves:

- **Squash** collapses the merge into a single-parent commit. The merge base falls back to the previous sync point, 64 upstream commits keep looking unmerged, and `Makefile`, `autotests/run.sh` and `autotests/run.cmd` conflict again on every future update, forever. Upstream's authorship is collapsed into yours, and the release tag can no longer be checked against the history.
- **Rebase** replays all upstream commits onto `master` one by one and fails almost immediately on the README.

The repository is configured to allow only merge commits (`allow_squash_merge` and `allow_rebase_merge` are off), and `master` is protected: pull requests only, both CI jobs required, no force pushes or deletions, enforced for admins.
If those settings are ever loosened, this rule still stands.

Note that `required_linear_history` must stay **off** - it would forbid the merge commits this workflow depends on.

### Automated weekly sync

`.github/workflows/upstream-sync.yml` runs every Monday at 04:17 UTC, and on demand via `workflow_dispatch`.
It fetches upstream, and if there is anything new and no sync pull request is already open, it merges, bootstraps, commits the regenerated `bootstrap/` artifacts, opens a pull request and turns on auto-merge.
The pull request lands by itself once both CI jobs pass; if they do not, it simply stays open.

The workflow deliberately **fails** rather than improvising in the two cases automation cannot handle:

- the merge conflicts - resolve by ownership, as above
- the bootstrap fails - usually upstream renamed or split modules again, so the module lists in `src/standalone-bootstrap.sh` and `src/standalone-bootstrap.cmd` need updating by hand

Both cases surface as a failed workflow run, which is what GitHub emails about.
That mail is the only alerting in place, so do not mute Actions notifications for this repository.

The workflow needs a fine-grained PAT with **Contents: read and write** and **Pull requests: read and write** on this repository, stored as the secret `SYNC_TOKEN` in the **`upstream-sync` environment** - not as a repository secret.
The default `GITHUB_TOKEN` cannot be used: pull requests opened with it do not trigger workflows, so the required checks would never run and the pull request could never merge.
The workflow checks for the secret first and fails with an explanatory message if it is missing.

The environment is restricted to the `master` branch, so the token is only readable by jobs running there.
This matters because a repository secret is readable by any workflow on any branch, and only `master` is protected - a workflow file pushed to a throwaway branch could otherwise read a token that has write access to contents and pull requests.
Scheduled workflows always run on the default branch, so the restriction costs the automation nothing; the one consequence is that a manual `workflow_dispatch` must be started from `master` or the secret will not resolve.

The job declares `environment: upstream-sync`, and it must keep doing so.
Without that key the environment secret is invisible to the job, and the run fails at the guard step as if the token had never been created.

Every `gh` call in the workflow passes `--repo "$GITHUB_REPOSITORY"` explicitly.
This is not decoration: the workflow adds an `upstream` remote, and `gh` then resolves a bare command in that checkout to `Mazdaywik/Refal-05` rather than to this fork.
Without `--repo`, `gh pr create` would target upstream's repository.

## Releases

`.github/workflows/release.yml` is triggered by hand (`workflow_dispatch`) and is the only supported way to publish a release.
Syncing is automatic, publishing is not: a release is something people download, so deciding that one is worth cutting stays a judgement call.

The tag is computed, not typed: `git merge-base HEAD upstream/master` gives the newest upstream commit contained in `master`, which is exactly the convention the README promises.
Pass the `tag` input only to override it, for instance to republish the same upstream commit after a packaging fix.
The workflow refuses to run if a release with that tag already exists.

Release binaries are built with release flags, not with the flags the bootstrap uses:

- Linux: `gcc -O2 -s -static`. Static because the ordinary build requires `GLIBC_2.34`, which rules out anything older than roughly 2021 - an odd requirement for a compiler whose whole pitch is that you only need a C89 toolchain.
- Windows: `cl /TC /W3 /wd4996 /O2 /MT`. `/MT` links the C runtime statically, so users do not need the Visual C++ Redistributable. The ordinary CI build uses the default `/MD` and does.

Optimisation is worth it and is safe: on the compiler's own sources `-O2` is about 1.4 to 1.5 times faster than the `-g` build, and the generated C is byte-identical across debug, optimised and static builds, so nothing about the output depends on the flags.

The Linux job bootstraps and tests with the default configuration first, then relinks with release flags and **runs the autotests again against the binary that will actually be published**.
Do not simplify that into a single optimised bootstrap: the point is that the artifact users download is the artifact that passed the tests.

## CI/CD

`.github/workflows/build.yml` triggers on pushes to `master`, pull requests targeting `master`, and manual `workflow_dispatch`, and builds on Linux and Windows in parallel.

- **Linux**: Ubuntu + GCC, runs `make bin/refal05c`, verifies the bootstrap fixpoint, uploads `bin/refal05c` as `refal05-linux` and `bootstrap/` as `bootstrap-artifacts-linux` (90 days); on failure uploads `autotests/__error.txt` as `test-errors-linux` (30 days)
- **Windows**: MSVC, writes its own `c-plus-plus.conf.cmd`, locates `vcvars64.bat` through `vswhere.exe` (the `windows-latest` image changes its Visual Studio version over time, so never hardcode that path again), runs `src\standalone-bootstrap.cmd`, uploads `bin\refal05c.exe` as `refal05-windows` and `bootstrap\` as `bootstrap-artifacts-windows`

The fixpoint check regenerates all eight files with the freshly built compiler and requires them to match `bootstrap/` byte for byte.
It runs on Linux only: the property being checked belongs to the compiler, not to the host, and the Windows job would only repeat it at the cost of another platform-specific path dance.
It is the check that makes unattended auto-merge defensible - the autotests can pass on a half-migrated compiler, the fixpoint cannot.

## Code Style

**Shell scripts**:

- Do not use inline comments in bash (`.sh`) or batch (`.cmd`) scripts
- Bash: `set -ex` for bootstrap scripts, explicit per-step error checks in test scripts
- Batch: `setlocal enabledelayedexpansion` and `if errorlevel` checks after every step

## Known Issues

- `autotests/run.cmd` puts a `:LOOP` label inside the parenthesised `else` block of the argument dispatch, which is not valid batch - a `goto` exits the block. Only the no-argument path (the `for` branch) is exercised by CI, so this has never been hit.
- `src/benchmark.prj` lists `LibraryEx.ref`, `R5FW-*.ref` and `Platform.ref`, none of which exist in `src/`. This is upstream's file and upstream's problem; the benchmark scripts are not exercised by CI.

## Important Notes

- The language is **Refal-05**, not full Refal-5 (a subset, with some differences in metafunctions)
- Entry point is always `$ENTRY GO`
- All source files use UTF-8 encoding
- The docs use non-breaking spaces (U+00A0) after single-letter Russian prepositions. Do not "clean" them up.
- Prebuilt Unix and Windows binaries are published as GitHub releases; the release tag matches the last upstream commit merged into this fork
