# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This repository is **a build, not a fork**.
It builds the [Refal-05](https://github.com/Mazdaywik/Refal-05) compiler without needing an external Refal-5 compiler for bootstrapping: a C89 compiler is enough.

Both upstream projects are git submodules, pinned and never edited here:

- `refal-05/` - the compiler itself, from `Mazdaywik/Refal-05`
- `refal-5-framework/` - the Refal-5 framework the compiler is built on, from `Mazdaywik/refal-5-framework`

Everything else in the tree belongs to this repository: `bootstrap/`, `Makefile`, `src/standalone-bootstrap.*`, `autotests/run.*`, `.github/`, `README.md`, `CLAUDE.md`.

**There is nothing here that can conflict with upstream.**
Earlier this repository was a fork that edited upstream files in place, and it cost 17 merge conflicts on the first real update, plus a commit that stripped ~2300 non-breaking spaces out of upstream's Russian documentation for no reason.
The submodule layout makes that class of mistake impossible rather than forbidden by convention.

If something needs fixing in either upstream, send it there.
This repository has no mechanism to carry a local patch, and that is deliberate.

## Bootstrap Architecture

1. **Bootstrap artifacts**: pre-compiled C files in `bootstrap/`, generated by the previous compiler build
2. **Stage 1**: compile the old compiler (`bin/refal05c-old`) from the bootstrap C files
3. **Stage 2**: use the old compiler to recompile the sources of both submodules into fresh C files
4. **Stage 3**: compile the new compiler (`bin/refal05c`) from the newly generated C files
5. **Validation**: run the autotests against the new compiler

**Every file in `bootstrap/` is regenerated on every bootstrap. There are no frozen artifacts.**

Its eight files come from two source trees:

- the compiler, from `refal-05/src/`: `main.c`, `generator.c`, `parser.c`
- the framework, from `refal-5-framework/lib/`: `LibraryEx.c`, `R5FW-Parser.c`, `R5FW-Plainer.c`, `R5FW-Transformer.c`, `Platform.c`

The compiler compiles the framework itself, exactly as upstream's own `refal-05/src/makeself.sh` does, so no external toolchain is involved.

`Platform.ref` is taken from `refal-5-framework/lib/posix/` on **both** platforms, deliberately: its `PathSeparator` returns `:`, so `R05PATH` is colon-separated everywhere.

This used to be otherwise, and the history is worth knowing.
Those five framework files were once committed as frozen C with no source in the repo, regenerable only with an external Refal-5, and drifting further from the framework with every release.
The frozen set was a framework version behind, still carrying a separate `R5FW-Parser-Defs.c` that the framework had already merged into `R5FW-Parser.ref`, and it worked only because the interface happened not to have changed.

### Always pass source paths with forward slashes

The compiler derives the output filename by stripping everything up to the last directory separator, and `IsDirectorySeparator` in `bootstrap/Platform.c` recognizes **only `/`**, never `\`.

Both bootstrap scripts therefore name modules as `refal-05/src/main`, with forward slashes, on **both** platforms.
The generated `.c` then lands in the current directory everywhere, and a single `mv *.c bootstrap` (or `move /Y *.c bootstrap\`) collects it.

Do not "fix" the Windows script to use backslashes: the output would land next to the sources, inside the submodules, leaving them dirty.
`autotests/run.cmd` converts `%TESTS_DIR%` to forward slashes (`%TESTS_DIR:\=/%`) for the same reason.

## Build Commands

### Linux/Unix

```bash
make bin/refal05c
```

Creates `c-plus-plus.conf.sh` from `refal-05/lib/c-plus-plus.conf.sh.template` if missing, runs `src/standalone-bootstrap.sh` for the full 3-stage bootstrap, then runs the autotests.

### Windows

```cmd
make bin/refal05c.exe
```

Or directly: `src\standalone-bootstrap.cmd`.
The Windows template has no active compiler and aborts until one of its sections is uncommented; CI writes its own configuration instead.

### Autotests

```bash
./autotests/run.sh
./autotests/run.sh type.ref arithmetic-32-bit.ref
```

The tests themselves live in `refal-05/autotests/` and belong to upstream.
Only the runners are ours.

Both runners work in a scratch directory, `.testrun/autotests/`, and delete it afterwards, so the submodule stays clean.
The directory has to be named `autotests`: `get-current-directory.ref` asserts that the current directory ends with `/autotests`.

- `.BAD-SYNTAX.ref` - compilation must fail with an error, and the compiler must not crash (exit code < 200)
- `.SATELLITE.ref` - helper module, compiled together with the test of the same base name, never run on its own
- `nested-comment.BAD-SYNTAX._ref` - disabled upstream; the `._ref` extension keeps it out of the `*.ref` glob

**Do not replace these with upstream's runners.** Upstream's `refal-05/autotests/run.sh` calls bare `exit` on every failure path, which exits with the status of the preceding `echo` - that is, `0` - so it can never fail CI.
This is worth sending upstream: its `run.cmd` handles failures correctly, so the two runners disagree about whether a failing test is a failure.

### Cleanup

```bash
make clear
```

## Key Directories and Files

- `refal-05/` - submodule: the compiler and its `lib/`, `docs/`, `autotests/`. Never edit.
- `refal-5-framework/` - submodule: the framework sources. Never edit.
- `bootstrap/` - generated C artifacts, committed; regenerated in full by every bootstrap
- `src/standalone-bootstrap.sh` / `.cmd` - the bootstrap
- `autotests/run.sh` / `.cmd` - test runners
- `bin/` - build output, gitignored: `refal05c` / `refal05c.exe` and the intermediate `refal05c-old`
- `c-plus-plus.conf.sh` / `c-plus-plus.conf.cmd` - created from the templates in `refal-05/lib/`, gitignored

## C Compiler Configuration

Default on Unix: `export R05CCOMP='gcc -Wall -g'`.

- `-DR05_SHOW_STAT` - compiler statistics; used by the bootstrap scripts
- `-DR05_SHOW_STAT_DETAILED` - per-function profiling hooks; without it `r05_this_is_generated_function`, `r05_start_e_loop` and `r05_stop_e_loop` compile to no-op macros
- `-DR05_NUMBER_INT` (default), `-DR05_NUMBER_LONG`, `-DR05_NUMBER_LONGLONG`, `-DR05_NUMBER_UINT32_T`, `-DR05_NUMBER_UINT64_T`, `-DR05_NUMBER_CUSTOM` - macro-digit size

`-DR05_POSIX` and `-DR05_CLOCK_SKIP` are obsolete: `refal05rts.h` auto-detects the platform, and the clock option is no longer referenced.

## Releases

`.github/workflows/release.yml` is triggered by hand and is the only supported way to publish.
The tag is the pinned `refal-05` revision (`git -C refal-05 rev-parse --short HEAD`), so it names exactly the upstream commit the binaries were built from.

Release binaries use release flags, not the bootstrap's:

- Linux: `gcc -O2 -s -static`. Static because the ordinary build needs `GLIBC_2.34`, ruling out anything older than roughly 2021.
- Windows: `cl /TC /W3 /wd4996 /O2 /MT`. `/MT` avoids requiring the Visual C++ Redistributable.

`-O2` is about 1.4 to 1.5 times faster than `-g` on the compiler's own sources, and the generated C is byte-identical across debug, optimised and static builds.

The Linux job bootstraps and tests with the default configuration, then relinks with release flags and **runs the autotests again against the binary that will actually be published**.

## CI/CD

`.github/workflows/build.yml` runs on pushes to `master`, pull requests, and manual dispatch, on Linux and Windows. Every checkout uses `submodules: recursive`.

The fixpoint check regenerates all eight files with the freshly built compiler and requires them to match `bootstrap/` byte for byte.
It runs on Linux only: the property belongs to the compiler, not the host.
It is the check that makes unattended auto-merge defensible - the autotests can pass on a half-migrated compiler, the fixpoint cannot.

### Automated weekly sync

`.github/workflows/upstream-sync.yml` runs every Monday at 04:17 UTC, and on demand.
It has two independent jobs, `sync-compiler` and `sync-framework`, one per submodule.
Each bumps its submodule to the upstream tip, bootstraps, commits the regenerated `bootstrap/`, opens its **own** pull request and turns on auto-merge.

Separate pull requests are deliberate: the two upstreams fail independently, so a framework change that breaks the bootstrap does not also block an unrelated compiler update from landing.

A job **fails** rather than improvising when the bootstrap fails after a bump - usually upstream renamed or split modules, so the module lists in `src/standalone-bootstrap.sh` and `src/standalone-bootstrap.cmd` need updating by hand.
That surfaces as a failed workflow run, which is what GitHub emails about; that mail is the only alerting in place, so do not mute Actions notifications.

The workflow needs a fine-grained PAT with **Contents: read and write** and **Pull requests: read and write**, stored as `SYNC_TOKEN` in the **`upstream-sync` environment** - not as a repository secret.
`GITHUB_TOKEN` cannot be used: pull requests opened with it do not trigger workflows, so the required checks would never run.
The environment is restricted to `master`, so a manual dispatch must be started from `master` or the secret will not resolve.
The jobs declare `environment: upstream-sync`, and must keep doing so.

Every `gh` call passes `--repo "$GITHUB_REPOSITORY"` explicitly.

Merges must be **merge commits**; squash and rebase are disabled on the repository, and `required_linear_history` must stay off.

## Important Notes

- The language is **Refal-05**, not full Refal-5 (a subset, with some differences in metafunctions)
- Entry point is always `$ENTRY GO`
- All source files use UTF-8 encoding
- Upstream's docs use non-breaking spaces (U+00A0) after single-letter Russian prepositions. Do not "clean" them up.
